## 末端目标「安全参数」落地（三条约束实现）

### 用户需求（逐字）

> 1. 硬误差保证在2%以内(限位可调)
> 2. 几何球壳的内径可调(选项在末端目标选择中支持修改，最小为0.1，其它方式不能变化)
> 3. 不影响任何算法，仅影响参数

决策点经确认：**只许向内收紧** / **选项 C（只加前置检查）** / **容差默认 0**。

### ★ 核心认知修正（最重要，勿忘）

**「限位可调」根本解决不了「手输被拒」。**

- `elbow` 限位 `[108.4414852068, 141.8582211436]` **恰好等于** `servo_8` 硬限位
  `20..100` 经标定（`reverse=true, scale=2.39401, offset=359.61`）反算的值
  ⇒ **放宽余量 = 0.000000°**。`shoulder` 同理（`servo_7` `80..160` → `[-6.093683, 49.454929]`）。
- ⇒ 限位**一个度都放不宽**（放宽 ⇒ `ACTUATOR_REACH` 校验失败）。
- 反过来，**收紧**只是把悬崖搬个位置 —— 新极限点回输仍被 `EPS_DEG = 1e-9` 拒。
- ⇒ **真正起作用的是「判据容差 T」**；「限位可调」只是可选的保守化手段。

### 2% 反推 T

最坏力臂 `L = l1 + l2 = 160`，钳位误差 `≈ L·sin(T)`，基准 `MEASURED_MAX_RADIUS_MM = 177.091`：

| T | 最坏位移 | % | 判定 |
|---|---|---|---|
| 0.5° | 1.396mm | 0.789% | ✅ |
| **1.0°** | 2.793mm | **1.577%** | ✅ ← 取为上限 |
| 2.0° | 5.585mm | 3.154% | ❌ |

## 末端目标「安全参数」改版：删限位调节 + 加球壳外径覆写

### 用户需求（逐字）

> 去除安全参数中的所有限位调节(同时删除后端相关可调参数），增加球壳外径覆写，
> 支持从1~160mm，启用修改后是实时变化并参与计算

### ★ 三个决定性认知（本轮实测，勿忘）

**① 外径覆写必须开在 `ik.ts` 里面。**
需求"参与计算"的落点是 2R 的 `cosAlpha`（`d² = l1²+l2²−2l1l2cos(π−θ)`）。
`if (d > reachMax)` 只决定"能不能解"，`cosAlpha` 才决定"解出来是多少"。
在 `ik.ts` 外面拦一道**只能实现"拒绝更早"**，不能实现"按新臂展求解"。
⇒ 本轮对 `ik.ts` 做**最小 opt-in**：`IkOptions.reachMaxMm?: number`。
`undefined` ⇒ 用求导外径，**语义一字节未变**（实测 `抽象层残差差 0.000e+0`）。

**② 外径覆写的有效区间远小于 UI 的 1~160。**

| 量 | 值 |
|---|---|
| 几何球壳 `ikGeometry().reach` | `[1.42e-14, 160]` |
| **合法限位域内实际腕枢轴距离 `d`** | **`[44.1665, 139.2662]`** |
| 最大点 | `shoulder=max, elbow=min` → `139.2662`（两杆近乎伸直） |
| 最小点 | `shoulder=min, elbow=max` → `44.1665`（折得最狠） |

⇒ 填 150/160 **等于没覆写**。UI 把 `max` 显示为 `min(160, 求导外径)`。

**③ 「限位可调」整段移除是有实测依据的**（不是嫌麻烦）：
关节限位映射到舵机后必须落在舵机硬限位内（`ACTUATOR_REACH`），
本机余量 **0.000000°** ⇒ 限位**一个度都放不宽**，"调节"只剩向内收紧，
而向内收紧已被**球壳内径覆写**更直接覆盖（1 个标量 vs 逐关节 2 端点）。
⇒ 删 `jointTightenDeg` / `tightenLimits()` / `applyJointTightening()` /
`modelWithTightening()` / `overrideCache` 全套。

### ★★ 两个测试构造坑（都导致过假性通过/失败）

1. **"外圈点"不能想当然。** 初版用 `reachable({shoulder:0, elbow:141})` 当外圈点，
   但它 `d` 只有 **19.5mm**（`shoulder=0` 让手臂折回）⇒ 用它验证"外径收紧拦住外圈"
   会假性通过。正解：`atOuterShell()` = `shoulder=max, elbow=min`（`d=139.2662`）。
2. **求 `radial` 不能用 `wrist.parentLink` 的长度。**
   `tcp.joint='tool'` 的 `parentLink` 是 **`forearm_link`(80)** 而非 `tool_link`(40)
   ⇒ 算出的 `d` 偏小（94.15 vs 真值 131.96），断言假性通过。
   正确口径：`radial = geometry.toolOffset[0] = model.tcp.offset` 的径向分量（= 40）。
   已在 helper 里加 `expect(pivotZ).toBeCloseTo(60)` / `expect(radial).toBeCloseTo(40)` 自校验。

## ★★ 事故：store 的 `d` 与 `ik.ts` 的 `d` 不是一个量（用户报"改小外径反而越界"）

### 用户报告

> 为什么本身可运行范围，我把外径覆写从160改到60，反而OUT_OF_SPACE了

### 根因：`wristDistance()` 把 `radial` 取错了连杆

`robotStore.ts` 的前置检查自己重算 `d`，其中

```ts
const radial = linkLengthOf(model, wrist.parentLink);   // ❌ wrist = model.tcp.joint = 'tool'
```

`tcp.joint='tool'` 的 `parentLink` 是 **`forearm_link`（80）**，不是 `tool_link`（40）。
而 `ik.ts` 的口径是 `toolOffset[0] = 40`（`requireConstantToolOffset()` 实测）。

同一目标点 ⇒ **两个 `d`**：

| 来源 | `radial` | `d`（同一点） |
|---|---|---|
| `ik.ts`（正确） | `toolOffset[0]` = 40 | **111.542** |
| `wristDistance()`（错） | `forearm_link` = 80 | **92.159** |

差 **19.38mm**，且**不报错**。函数注释还写着"`radial` = `tool_link.length`（本机 40）" ——
**注释与代码不一致**，注释描述的是意图，代码读的是另一个连杆。

### 症状为什么迷惑人

- 错误 `d` **系统性偏小**（`radial` 越大 ⇒ `|r − radial|` 越小），偏 19~40mm
- 后果 ①：**内圈一大片实际不可达的点被显示成可达** ⇒ 用户以为"可运行范围"更大
- 后果 ②：把外径降到 60 时，真实 `d=111.5` 当然超 60；而那个点在**外径 160 下本来就失败**
  （只是原因不同：`JOINT_LIMIT @ elbow` 而非 `OUT_OF_WORKSPACE`）
  ⇒ 所以**报错是"碰巧对"的**：判定结果对，依据的数是错的
- 后果 ③（更危险）：口径不一致 ⇒ 两层的拒绝理由随机（有时这层、有时 `ik.ts` 那层）

### 修复：删掉自研几何，一律转发 `ik.ts`

```ts
function wristDistance(model, target): number {
  const geometry = ikGeometry(model);
  const { dr, dz } = wristSagittal(geometry, target);
  return Math.hypot(dr, dz);
}
function reachShellOf(model): readonly [number, number] {
  return ikGeometry(model).reach;   // 也是转发，理由同上
}
```

- `reachShellOf()` 原本自己按 `[|l1−l2|, l1+l2]` 从连杆表读 —— 本机数值恰好一致，
  但**不是同一份真值**（`ikGeometry()` 是从 FK 采样反推）。一并改为转发。
- 副作用：`robotStore.ts` 的 import 多取 `ikGeometry` / `wristSagittal`
  ⇒ **已登记进 `corePackageBoundary.test.ts` 的 ALLOWED 白名单**（双向断言：多取/少取都失败）。
- `dWrist` 类型 `number | null` → `number`，调用点改判 `reachOverridden`。

### ★ 教训（写进铁律）

**「同一个量只能有一套口径」不是洁癖，是这条规则真的会以"轻微、随机、不报错"的方式咬人。**
凡是"为了不扩依赖边而自己重算一遍真值"的写法，都是这个 bug 的温床 ——
`ik.ts` 里恰好有一个 `requireConstantToolOffset()` 专门用三个姿态交叉验证这个偏移常量，
**说明这个量本来就容易算错**，更不该在第二处重算。

⚠️ 注意我在**上一轮就已经在测试 helper 里踩过同一个坑并修掉了**
（`targetGuardParams.test.ts` 的 `wristDistanceOf`），但**没有回头查生产代码**。
⇒ 教训 2：**在测试里发现的口径坑，必须立刻回头 grep 生产代码有没有同款。**

### 新增回归断言

`targetGuardParams.test.ts` 加 `★★ 前置检查的 d 必须与 ik.ts 同口径`：
用极小外径（= `REACH_MAX_FLOOR_MM`）强制前置检查触发，从错误消息抠出 store 算的 `d`，

## 五、状态回传完整性分析（摇杆动了下位机，上位机能不能跟随）

**问题**：通过摇杆把机械臂调 30°，MeArm-3D 上位机状态是否跟随？
要求用 sim2sim 仿真、改下位机 sim 值，看界面是否所有数据同步更新。

**结论**：分两半 —— 「上位机下发」这条路**完整同步**；「下位机自主变化」这条路**整条是断的**。

### 实测证据一：报文级判决（喂固件真实报文给 controller）

```
① STATE 0.00 30.00 120.00 50.00        → ✅ 状态更新
② OK JOY S6=90 S7=90 S8=90 S9=90       → ❌ 上位机无感（摇杆走这条）
③ STATUS S6=90(H) S7=90(H) …           → ❌ 上位机无感
④ OK SET S9=120 S7=131                 → ❌ 上位机无感
⑤ STATE …（假设固件将来主动上报）        → ✅ 状态更新
```

**只有 `STATE <四个数值>` 这一种格式能更新状态**，而它**正是后端自己在
`execJR` / `execStatus` 时合成出来的**（`serial.go` 的 `default` 分支注释原文：
「回执原样转发但**不合成**任何关节级回执」）。
⑤ 是关键：**通路已就绪，缺的是"固件主动上报"和"后端轮询"**，不是缺解析能力。

### 实测证据二：端到端 + 界面（Go 后端 sim + Vite + CDP 读 DOM）

- 新客户端接入即收 `hello` + 一条 `joint_state` ⇒ **接入即推当前状态**（好的）
- A 客户端发命令，B 客户端收到**同一批 9 条** `joint_state` ⇒ **广播完整**
- 收敛轨迹 `shoulder 4.18 → 7.52 → … → 30.0000`（20ms tick、240°/s，非等值回显）
- **静置 2s 新增 0 条** ⇒ 无外部输入时链路静默，sim/后端都不主动报

CDP 实测（外部 WS 客户端下发 A 组→B 组，界面 DOM 取值）：

```
base      A组界面=-30  →  B组界面=30   ✅
shoulder  A组界面=10   →  B组界面=45   ✅
elbow     A组界面=130  →  B组界面=115  ✅
gripper   A组界面=30   →  B组界面=90   ✅
```

**Actual 列 / 3D 实际臂 / 误差面板 / TCP 误差 / 健康结论** 全部跟随。

⚠️ 但 **Command 列不跟随**（它是本客户端的意图），于是界面立刻变成
「异常：命令已静止但误差停在 60.00° —— 查卡死 / 失步 / 限位截断」、误差条 4 条全红。
**在摇杆场景下这是持续误报** —— 真实原因不是卡死，是「别的入口动了机器」，
而 UI 没有"外部来源"这个概念。

### 实测证据三：sim 下位机的命令接受面

```
JOY 9 900 / JOY 900 200 512 800   → ERR UNKNOWN      ← 真机摇杆命令 sim 不认
SET 9 120 / S9=120                → ERR UNKNOWN      ← 真机直控 sim 不认
STATUS                            → STATUS S9=90…   ← 格式不被 ParseReply 识别
JR 0 30 120 50                    → OK JR + 一串 STATE ✅ 唯一可用
```

⇒ **"在 sim 上模拟摇杆改动下位机"这条路，当前代码里走不通** ——
sim 只实现关节级 `JR`，真机那套舵机级入口它一概没有。
（另：sim 的 `STATUS` 回执格式与真机一致，但 `serial.go` 有 `execStatus` 翻译层、
sim 没有 —— 这是 sim 与 serial 的一处**不对称**。）

### 缺口定位（三层）

| 层 | 现状 |
|---|---|
| 固件 | **没有 JR / STATE**（`core/cmd.c` 只有 SET/JOY/IR/RESET/STATUS）；协议文档开头就写着「§4 的固件侧 `JR`/`STATE` 仍待实现」。摇杆/红外改完舵机**不回吐**任何东西 |
| 后端 | 只在**自己发起**的三条路径（JR / STATUS / RESET）上合成 STATE；`forward()` 对被动收到的行只记日志。**无周期轮询** —— `STATUS` 只在暖机时发一次（把 DTR 复位后弹回 90° 的真相拉回来） |
| 前端 | 无"外部来源"概念，外部动作会被判成链路异常 |

### ⚠️ 还有一条容易忽略的：摇杆网关会抢串口

`MeArm-RemoteControl`（9001 端口那个摇杆台）用 `serial.Open` **独占串口**，
而 MeArm-3D backend 的 `device.mode=serial` 也要开同一个口 ⇒ **两者不能同时连**。
所以若摇杆由它驱动，MeArm-3D 界面不是"不跟随"，而是**根本连不上设备**。

### 定稿的设计：两条上报路径必须分流

| 来源 | 设备回吐 | 后端标注 |
|---|---|---|
| `JR` 受理 | `STATE …`（关节角，命令引起） | `origin=command` |
| `SET`/`JOY`/`S<n>=` | `# SERVO …`（舵机角，设备侧自主变化） | `origin=device` |

⇒ **跟随与否只能由显式标注 `origin` 决定**，未知取值一律按 `command` 降级。
